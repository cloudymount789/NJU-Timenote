# NJU Timenote 前端 AI 协作指南

本文档用于长期保存项目的前端协作原则。每次开启新的 AI Agent、让 AI 修改代码、拆分页面任务、或上下文被压缩后，都应优先阅读本文档，再阅读具体任务文档。

目标不是让 AI 一次性写完整个前端，而是用稳定的工程护栏，让每个小功能都能被清楚实现、人工验证、及时回退，并持续维护代码仓库的可理解性。

## 1. 项目定位

- 项目名称：NJU Timenote。
- 技术方向：Flutter 前端，未来接入真实后端。
- 当前输入材料：
  - 高保真 UI 原型：位于 `UI/nju-timenote.pen`，可通过 Pencil 的 NCP/MCP 能力读取页面结构。
  - 页面交互逻辑：`UI/interaction.md`。
- 当前核心模块：
  - 首页。
  - 课表。
  - 添加课表。
  - 待办列表。
  - 待办筛选。
  - 待办详情。
  - 待办搜索。
  - 下一件事推荐。
  - 一句话创建待办。
  - 大目标拆分。

## 2. 总体协作原则

### 2.1 小步交付

- 不要一次性实现过多页面或流程。
- 每次任务应围绕一个清晰的页面、状态流或组件族。
- 每个功能完成后，应留给产品经理手动测试。
- 手动测试通过后，再继续下一组功能。

每轮流程：

1. 读取原型与交互文档。
2. 为当前页面产出实现计划。
3. 明确需要产品经理确认的问题。
4. 实现页面或功能。
5. 更新代码地图与接口文档。
6. 运行格式化、静态检查、必要测试。
7. 提交 Git commit。
8. 自行检查是否有不符合正常逻辑的实现，在回话后输出并列出，询问是否修正（跳出任务的要求，自行检查并思考）
9. 产品经理手动测试。

### 2.2 AI 不应机械复刻原型

高保真原型用于表达视觉方向、布局结构和交互意图，如背景，模块阴影，圆角等审美方面的都符合应高保真原型。但在逻辑方面：

AI 在实现时必须区分：

- 原型中的示例数据：仅用于理解界面，不应硬编码为真实初始数据。
- 真实应用的初始状态：应为空状态、加载状态、错误状态、无权限状态等合理状态。
- 真实后端数据：必须通过数据层、Repository、接口模型或 Mock Adapter 进入界面。

AI 可以使用 mock 数据辅助开发和测试，但必须满足：

- mock 数据集中放置，不散落在 UI 组件中。
- mock 与真实接口共用同一套 model/repository 抽象。
- 默认应用启动不应伪装成已经有真实业务数据。
- mock 开关、fake repository 或 fixture 的用途必须写入文档。

### 2.3 AI 必须主动识别不合理交互

当交互逻辑没有写清楚、存在歧义、可能反直觉、或与平台习惯冲突时，AI 不应直接乱猜。

AI 应在计划阶段提出问题，例如：

- 返回路径是否固定，还是返回来源页面？
- 删除、批量完成等高风险操作是否需要二次确认？
- 创建失败后是否保留表单内容？
- 网络失败、空数据、权限失败、识别失败时怎么展示？
- 选择器中非法范围应禁用、自动修正，还是提示错误？

如果问题不阻塞当前小步实现，可以先采用保守默认方案，并在任务文档中标记 `待产品确认`。

## 3. Harness Engineering 要求

这里的 Harness Engineering 指：不要让 AI 每次都读取整个项目，而是为 AI 提供稳定的、低 token 的工程上下文，让它能可靠地修改局部代码。

### 3.1 必须维护的文档

后续代码仓库中至少维护这些文档：

- `docs/ai-frontend-collaboration-guide.md`：本文档，记录长期协作原则。
- `docs/code-map.md`：代码地图，记录目录结构、核心模块、关键文件职责、常见修改入口。
- `docs/frontend-backend-contract.md`：前后端接口契约，已经由后端给出，不要修改，实在有要修改的地方需要先指出，由我和后端协商后再决定允不允许修改。
- `docs/frontend-roadmap.md`：前端推进计划，记录页面拆分、优先级、验收状态。

每次 AI 修改代码时，必须检查是否需要同步更新这些文档。只要新增、移动、重命名或改变重要职责，就必须更新 `docs/code-map.md`。

> 注意：如果发现文档被修改，不要改回原来你写的样子，大概率是人修改的，你只需要先遵循。

### 3.2 每个新 Agent 的默认读取顺序

新 Agent 不应一上来读取全仓库。顺序：

1. `docs/ai-frontend-collaboration-guide.md`
2. 当前任务说明
3. `docs/code-map.md`
4. 与当前任务相关的接口部分
5. 与当前任务相关的交互原文：`UI/interaction.md`
6. 读取 Pencil 原型中对应页面结构

### 3.3 代码地图应记录什么

`docs/code-map.md` 应用简短、稳定的方式记录：

- Flutter 入口文件。
- 路由定义位置。
- 主题、颜色、字体、圆角、阴影等设计 token 的位置。
- 各页面所在目录。
- 通用组件所在目录。
- 数据模型所在目录。
- Repository、API client、mock/fake 数据所在目录。
- 状态管理方案与 provider/controller/bloc 的位置。
- 常见修改任务对应应读文件列表。
- 等等

代码地图不是源码复述，不写大段实现细节，只写“改哪里、看哪里、不要碰哪里”。

## 4. Flutter 工程建议


### 4.1 推荐目录结构

初始结构可以按 feature 拆分：

```text
lib/
  main.dart
  app/
    app.dart
    router.dart
    theme/
  core/
    network/
    errors/
    widgets/
    utils/
  features/
    home/
    schedule/
    todo/
    recommendation/
  data/
    models/
    repositories/
    sources/
      remote/
      mock/
```

原则：

- 页面 UI 不直接调用 HTTP。
- 页面 UI 不硬编码业务数据。
- 页面通过状态管理层调用 repository。
- repository 隐藏真实后端与 mock 数据源差异。
- model 和接口契约保持一致。
- 通用视觉规范进入 theme/design tokens，不散落在页面里。

## 5. 视觉与体验要求

AI 实现前端时必须尊重高保真原型的视觉方向：

- 背景、模块阴影、圆角、间距、字体层级应贴近原型。
- 页面不能有明显“AI 味”：避免模板化卡片堆砌、默认 Material 风格裸奔、过度渐变、过度圆角、杂乱阴影。
- 页面动效应自然服务于交互，而不是机械跳转。
- 列表、筛选、详情、创建等高频操作要优先保证效率和稳定。
- 所有文字必须适配小屏，不能溢出、重叠或遮挡。
- 图标按钮应优先使用语义清晰的图标，并保留可访问性描述。
- 空状态、加载态、错误态、禁用态都需要设计。

课表页面有额外要求：

- 主色为蓝、紫、粉三种低饱和高明度色。
- 同一节课必须颜色一致。
- 表格线颜色浅。
- 课程块尽量占满格子，保留圆角，不应出现明显缝隙。
- 跨多个节次的课程连续显示。
- 跨上下午的课程应切割成两个块。
- 冲突课程应在同一格内左右排列。

## 6. 后端接口与数据边界

项目未来会接入真实后端，因此从第一天开始就按真实接口思维组织代码。

### 6.1 前端校验职责

前端必须处理常见可预见异常，不应全部交给后端：

- 必填字段为空。
- 结束时间早于开始时间。
- 结束节次小于开始节次。
- 小目标日期早于今天。
- 小目标日期晚于最终 DDL。
- 删除、批量删除、批量完成前的二次确认。
- 搜索无结果。
- 待办为空。
- 推荐待办时用户没有任何待办。

后端仍应做最终校验，前端校验用于提升体验。

## 7. Git 与回退规则

- 每完成一个可独立验证的小功能，应进行一次 Git commit。
- commit 前应运行格式化、静态检查和必要测试。
- commit 信息应说明完成的页面或功能，例如：
  - `feat(todo): add task detail editing shell`
  - `docs: add frontend collaboration guide`
  - `feat(schedule): render weekly timetable grid`
- 不要把无关改动混入同一个 commit。
- 如果工作区已有他人改动，AI 不得擅自回滚。
- 如果改动失败，应优先通过 Git commit 粒度回退，而不是大范围重写。

## 8. 单个任务的标准提示词模板

后续让 AI 修改代码时，建议使用下面的任务模板。

```md
你是本仓库的 Flutter 前端工程 Agent。请先阅读：

1. @docs/ai-frontend-collaboration-guide.md
2. @docs/code-map.md
3. @docs/frontend-backend-contract.md 中与本任务相关的部分
4. @UI/interaction.md 中与本任务相关的部分

本次任务：
【填写要做的页面或功能】

设计依据：
请使用pencil的mcp阅读高保真原型
【填写 Pencil 原型页面名称或截图说明】

```

## 9. 已确认产品决策

本节记录产品经理已经明确的要求。后续 Agent 不应反复追问这些问题，除非实现时发现它们与代码、接口契约或原型存在冲突。

### 9.1 平台与适配

- 首发平台：Android。
- 当前阶段以手机竖屏为主。
- 平板、横屏、桌面端、Web、iOS 适配以后再做。
- 暂无指定测试机型，前端实现时应至少保证常见 Android 手机尺寸不溢出、不遮挡。

### 9.2 视觉规范

- 高保真原型已经确定字号、颜色、圆角等关键视觉规范；阴影至少应以原型可见效果为准。
- 所有字体统一使用思源宋体。
- 思源宋体对应 Adobe Source Han Serif，官方仓库显示其使用 SIL Open Font License 1.1；一般可以随 App 打包、嵌入和分发，但不得单独售卖字体文件，且随包分发时应保留版权与许可证文本。实现时应在字体资源目录或第三方声明中保留 `LICENSE.txt`。
- 暗色模式需要，但当前 MCP 阶段先不做。实现主题时应避免把颜色硬编码到页面深处，给未来暗色模式留空间。
- App logo 未来会有，当前没有。
- 启动页还没确定，当前不作为开发重点。
- 图标规范没有固定体系，原则是用户看得懂、语义清楚、不要为了好看牺牲识别性。

### 9.3 数据、后端与离线

- 当前不需要登录。
- 课程、待办、标签、设置等业务数据优先存本地。
- 后端已有接口文档：`docs/frontend-backend-contract.md`。该文档是前后端契约，前端 Agent 不得擅自修改。
- 当前不做云端同步和多设备同步，未来再考虑。
- 离线状态下必须允许查看和编辑本地数据。
- 当前不需要同步队列。同步队列指“离线编辑后先记录一批待上传操作，等网络恢复再按顺序同步到云端”的机制；因为当前没有云端同步，所以 MCP 阶段不做。

### 9.4 课表规则

- 当前只做一个学校，课表节次时间先按 UI 原型来。
- 未来希望支持其他学校，因此节次时间、每天第几节、每节开始结束时间应抽象到设置或配置层，不要写死在课表 Widget 内。
- 学年/学期有几周需要未来在设置里由用户自己设定；高保真原型暂时缺设置界面。
- 当前以 `docs/frontend-backend-contract.md` 为准，初始支持 1-25 周。
- 法定节假日、调休、临时停课、补课当前不做。
- 对上述特殊日程，当前只提示用户需要手动调整；未来可能适配教务系统导入。
- 课程颜色以 `docs/frontend-backend-contract.md` 为准，按课程名称稳定生成，同一课程名在不同教学周保持同色。
- 颜色实现建议：当课程名第一次出现时，从符合视觉规范的蓝、紫、粉低饱和高明度色板中随机分配一个 `colorKey`，并保存“课程名 -> colorKey”的本地映射；之后同名课程必须复用该颜色，不能每次刷新重新随机。

### 9.5 待办规则

- 有持续时间的待办可以完成。
- 有持续时间的待办在结束时间过去后，应自动变成完成状态。
- 有持续时间的待办在结束时间到达前，不能被手动设为完成。
- 待办详情页不允许手动完成有持续时间的待办。
- 批量完成不应完成有持续时间的待办，应跳过。
- 重要程度使用半星点击输入。
- tag 当前为每个设备本地数据，因为当前没有用户体系。
- 重复待办生成规则由前端本地负责，但 MCP 阶段先只保存 `repeatRule`，不自动生成重复实例。
- 未来实现重复生成时建议采用本地规则引擎：`daily` 在下一天生成下一条实例，`weekly` 在下一周同一天生成下一条实例；生成动作应避免重复创建，且需要清楚区分“重复模板”和“具体待办实例”。该能力进入未来功能，不在当前 MCP 阶段强行实现。

### 9.6 智能能力

- 一句话智能创建待办未来会接 AI 后端，但当前还不做真实 AI。
- MCP 阶段仍要保留前端入口和接口边界。
- 当前临时行为：把用户输入的整句话直接作为待办名称，创建一个普通待办；实现上必须封装在智能解析 service/repository 后面，方便未来替换为真实 AI。
- 截图识别课表当前阶段需要做前端流程，但识别服务还没确定。
- 截图识别结果写入前必须让用户确认，不能识别完直接入库。
- 下一件事推荐未来会接 AI 接口。
- 当前临时推荐策略：从已有待办中 roll 出若干项；有 tag 时可按 tag 分组或加权 roll，没有 tag 时从全部待办中 roll；“其他可以做的事”从前端维护的一组本地建议中 roll。
- 大目标拆分当前是纯手动拆分，需要用户自己填写。
- 大目标拆分未来可能加入 AI 自动拆分，因此页面和数据层要为“AI 建议草稿”预留扩展点。

### 9.7 验收、截图与提交

- 每个可独立验证的小功能完成后，AI 应自动 Git commit。
- commit 前应运行可用的格式化、静态检查和必要测试。
- 需要截图对比原型。
- 对比原型时，应重点检查布局、字号、颜色、圆角、阴影、间距、层级和主要交互状态。
- MCP 阶段仍坚持小步实现、小步手测，不要因为自动 commit 就一次性塞入大量功能。
