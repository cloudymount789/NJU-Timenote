# NJU Timenote 前端 AI 协作指南

本文档用于长期保存项目的前端协作原则。每次开启新的 AI Agent、让 AI 修改代码、拆分页面任务、或上下文被压缩后，都应优先阅读本文档，再阅读具体任务文档。

目标不是让 AI 一次性写完整个前端，而是用稳定的工程护栏，让每个小功能都能被清楚实现、人工验证、及时回退，并持续维护代码仓库的可理解性。

## 1. 项目定位

- 项目名称：NJU Timenote。
- 技术方向：Flutter 前端，未来接入真实后端。
- 当前输入材料：
  - 高保真 UI 原型：位于 `UI/nju-timenote.pen`，可通过 Pencil 的 NCP/MCP 能力读取页面结构。
  - 页面交互逻辑：`UI/interaction.md`。
- 当前核心模块：
  - 首页。
  - 课表。
  - 添加课表。
  - 待办列表。
  - 待办筛选。
  - 待办详情。
  - 待办搜索。
  - 下一件事推荐。
  - 一句话创建待办。
  - 大目标拆分。

## 2. 总体协作原则

### 2.1 小步交付

- 不要一次性实现过多页面或流程。
- 每次任务应围绕一个清晰的页面、状态流或组件族。
- 每个功能完成后，应留给产品经理手动测试。
- 手动测试通过后，再继续下一组功能。
- 如果任务拆分后仍然需要大量上下文，应继续拆小。

推荐节奏：

1. 读取原型与交互文档。
2. 为当前页面产出实现计划。
3. 明确需要产品经理确认的问题。
4. 实现页面或功能。
5. 更新代码地图与接口文档。
6. 运行格式化、静态检查、必要测试。
7. 提交 Git commit。
8. 产品经理手动测试。

### 2.2 AI 不应机械复刻原型

高保真原型用于表达视觉方向、布局结构和交互意图，但不等于真实 App 的最终状态。

AI 在实现时必须区分：

- 原型中的示例数据：仅用于理解界面，不应硬编码为真实初始数据。
- 真实应用的初始状态：应为空状态、加载状态、错误状态、无权限状态等合理状态。
- 真实后端数据：必须通过数据层、Repository、接口模型或 Mock Adapter 进入界面。

AI 可以使用 mock 数据辅助开发和测试，但必须满足：

- mock 数据集中放置，不散落在 UI 组件中。
- mock 与真实接口共用同一套 model/repository 抽象。
- 默认应用启动不应伪装成已经有真实业务数据。
- mock 开关、fake repository 或 fixture 的用途必须写入文档。

### 2.3 AI 必须主动识别不合理交互

当交互逻辑没有写清楚、存在歧义、可能反直觉、或与平台习惯冲突时，AI 不应直接乱猜。

AI 应在计划阶段提出问题，例如：

- 返回路径是否固定，还是返回来源页面？
- 删除、批量完成等高风险操作是否需要二次确认？
- 创建失败后是否保留表单内容？
- 网络失败、空数据、权限失败、识别失败时怎么展示？
- 选择器中非法范围应禁用、自动修正，还是提示错误？

如果问题不阻塞当前小步实现，可以先采用保守默认方案，并在任务文档中标记 `待产品确认`。

## 3. Harness Engineering 要求

这里的 Harness Engineering 指：不要让 AI 每次都读取整个项目，而是为 AI 提供稳定的、低 token 的工程上下文，让它能可靠地修改局部代码。

### 3.1 必须维护的文档

后续代码仓库中至少维护这些文档：

- `docs/ai-frontend-collaboration-guide.md`：本文档，记录长期协作原则。
- `docs/code-map.md`：代码地图，记录目录结构、核心模块、关键文件职责、常见修改入口。
- `docs/api-contract.md`：前后端接口契约，记录接口、请求响应模型、错误码、状态约定。
- `docs/frontend-roadmap.md`：前端推进计划，记录页面拆分、优先级、验收状态。
- `docs/manual-test-checklist.md`：人工测试清单，记录每个页面和流程的手测步骤。

每次 AI 修改代码时，必须检查是否需要同步更新这些文档。只要新增、移动、重命名或改变重要职责，就必须更新 `docs/code-map.md`。只要新增或调整后端交互，就必须更新 `docs/api-contract.md`。

### 3.2 每个新 Agent 的默认读取顺序

新 Agent 不应一上来读取全仓库。推荐顺序：

1. `docs/ai-frontend-collaboration-guide.md`
2. 当前任务说明
3. `docs/code-map.md`
4. 与当前任务相关的接口部分：`docs/api-contract.md`
5. 与当前任务相关的交互原文：`UI/interaction.md`
6. 必要时读取 Pencil 原型中对应页面结构
7. 只读取代码地图指出的相关源码文件

### 3.3 代码地图应记录什么

`docs/code-map.md` 应用简短、稳定的方式记录：

- Flutter 入口文件。
- 路由定义位置。
- 主题、颜色、字体、圆角、阴影等设计 token 的位置。
- 各页面所在目录。
- 通用组件所在目录。
- 数据模型所在目录。
- Repository、API client、mock/fake 数据所在目录。
- 状态管理方案与 provider/controller/bloc 的位置。
- 常见修改任务对应应读文件列表。

代码地图不是源码复述，不写大段实现细节，只写“改哪里、看哪里、不要碰哪里”。

## 4. Flutter 工程建议

以下为初始建议，最终以项目实际搭建结果为准。

### 4.1 推荐技术选型

- Flutter 稳定版。
- Dart null safety。
- 路由：`go_router`。
- 状态管理：优先考虑 `Riverpod` 或 `Bloc`，二选一，不混用。
- 网络：`dio` 或官方 `http`，配合统一 API client。
- 数据模型：`freezed` + `json_serializable`，或手写 immutable model。项目复杂度上来后推荐生成式 model。
- 本地持久化：搜索历史、草稿、简单设置可用 `shared_preferences`；复杂离线数据再考虑 `drift` 或 `isar`。
- 动效：优先使用 Flutter 原生隐式动画、Hero、PageRouteBuilder、AnimatedSwitcher、Sliver 等，不为了炫技引入重依赖。

### 4.2 推荐目录结构

初始结构可以按 feature 拆分：

```text
lib/
  main.dart
  app/
    app.dart
    router.dart
    theme/
  core/
    network/
    errors/
    widgets/
    utils/
  features/
    home/
    schedule/
    todo/
    recommendation/
  data/
    models/
    repositories/
    sources/
      remote/
      mock/
```

原则：

- 页面 UI 不直接调用 HTTP。
- 页面 UI 不硬编码业务数据。
- 页面通过状态管理层调用 repository。
- repository 隐藏真实后端与 mock 数据源差异。
- model 和接口契约保持一致。
- 通用视觉规范进入 theme/design tokens，不散落在页面里。

## 5. 视觉与体验要求

AI 实现前端时必须尊重高保真原型的视觉方向：

- 背景、模块阴影、圆角、间距、字体层级应贴近原型。
- 页面不能有明显“AI 味”：避免模板化卡片堆砌、默认 Material 风格裸奔、过度渐变、过度圆角、杂乱阴影。
- 页面动效应自然服务于交互，而不是机械跳转。
- 列表、筛选、详情、创建等高频操作要优先保证效率和稳定。
- 所有文字必须适配小屏，不能溢出、重叠或遮挡。
- 图标按钮应优先使用语义清晰的图标，并保留可访问性描述。
- 空状态、加载态、错误态、禁用态都需要设计。

课表页面有额外要求：

- 主色为蓝、紫、粉三种低饱和高明度色。
- 同一节课必须颜色一致。
- 表格线颜色浅。
- 课程块尽量占满格子，保留圆角，不应出现明显缝隙。
- 跨多个节次的课程连续显示。
- 跨上下午的课程应切割成两个块。
- 冲突课程应在同一格内左右排列。

## 6. 后端接口与数据边界

项目未来会接入真实后端，因此从第一天开始就按真实接口思维组织代码。

### 6.1 必须抽象的数据对象

至少应提前定义以下领域模型：

- Course：课程。
- CourseTimeSlot：课程时间与周次规则。
- Todo：待办。
- TodoTag：标签。
- TodoFilter：待办筛选条件。
- RecommendationRequest：下一件事推荐输入。
- RecommendationResult：下一件事推荐结果。
- GoalBreakdownDraft：大目标拆分草稿。
- GoalSubtask：拆分后的小目标。

### 6.2 接口文档必须包含

`docs/api-contract.md` 中每个接口至少记录：

- 接口用途。
- HTTP method 与 path。
- 请求参数。
- 请求体。
- 响应体。
- 空状态约定。
- 错误状态约定。
- 前端是否需要乐观更新。
- 是否需要分页。
- 是否需要本地缓存。
- 当前实现状态：`planned` / `mocked` / `implemented` / `changed`。

### 6.3 前端校验职责

前端必须处理常见可预见异常，不应全部交给后端：

- 必填字段为空。
- 结束时间早于开始时间。
- 结束节次小于开始节次。
- 小目标日期早于今天。
- 小目标日期晚于最终 DDL。
- 删除、批量删除、批量完成前的二次确认。
- 搜索无结果。
- 待办为空。
- 推荐待办时用户没有任何待办。

后端仍应做最终校验，前端校验用于提升体验。

## 7. Git 与回退规则

- 每完成一个可独立验证的小功能，应进行一次 Git commit。
- commit 前应运行格式化、静态检查和必要测试。
- commit 信息应说明完成的页面或功能，例如：
  - `feat(todo): add task detail editing shell`
  - `docs: add frontend collaboration guide`
  - `feat(schedule): render weekly timetable grid`
- 不要把无关改动混入同一个 commit。
- 如果工作区已有他人改动，AI 不得擅自回滚。
- 如果改动失败，应优先通过 Git commit 粒度回退，而不是大范围重写。

## 9. 建议的开发拆分

以下拆分用于避免一次性完成过多内容。每一步完成后建议人工手测。

### 阶段 0：工程基建

- 创建 Flutter 项目。
- 建立路由、主题、目录结构。
- 建立代码地图、接口文档、测试清单。
- 接入基础状态管理。
- 建立 mock repository 与真实 repository 的切换边界。

验收：App 可启动，有空白或占位首页，路由和主题能工作。

### 阶段 1：首页壳与全局导航

- 实现首页静态结构。
- 实现设置、课表、待办、搜索、创建待办、下一件事入口的路由跳转。
- 底部输入栏唤起创建待办浮层。

验收：首页视觉接近原型，所有入口能到对应占位页面。

### 阶段 2：待办基础闭环

- 待办列表。
- 待办详情。
- 创建待办浮层。
- 手动创建待办。
- 完成、删除、编辑基础字段。

验收：可以从空状态创建待办、编辑、完成、删除，刷新后状态一致。

### 阶段 3：待办增强

- 筛选边栏。
- 搜索。
- 批量操作。
- tag 选择与新增。
- 重复设置。

验收：筛选、搜索、批量选择与详情编辑互相不冲突。

### 阶段 4：课表

- 课表网格渲染。
- 课程颜色策略。
- 课程跨节次、跨上午下午切割。
- 冲突课程布局。
- 手动添加课程。
- 删除课程。

验收：多种边界课程都能正确显示，添加删除后列表刷新。

### 阶段 5：智能能力入口

- 一句话创建待办接口边界。
- 截图识别添加课程接口边界。
- 下一件事推荐。
- 大目标拆分。

验收：接口未完成时也有清晰 loading/error/empty 状态；接口完成后可替换 mock。

### 阶段 6：体验打磨

- 页面转场动效。
- 列表动效。
- 表单焦点与键盘处理。
- 小屏适配。
- 暗色模式或主题适配，如果需要。
- 可访问性检查。

验收：主流程在目标设备上可流畅操作，没有明显跳变、遮挡、溢出。

## 10. 需要产品经理确认的问题

以下问题会直接影响前端架构、接口契约或交互实现。建议你逐条回答，回答后应更新本文档或新增决策记录。

### 10.1 平台与设备

1. 首发平台是 Android、iOS、Web，还是三者都要？
2. 是否需要适配平板、横屏或桌面端？
3. 目标屏幕尺寸是否以手机为主？是否有指定测试机型？

### 10.2 视觉规范

1. 高保真原型中是否已经确定字体、字号、颜色、圆角、阴影？
2. `UI/字体.txt` 中的字体是否必须在 App 中使用？是否有授权问题？
3. 是否需要暗色模式？
4. 是否已有 App logo、启动页、图标规范？

### 10.3 后端与登录

1. 是否需要用户登录？如果需要，登录方式是什么？
2. 后端是否已有接口文档？如果没有，前端是否可以先定义草案接口？
3. 数据是否需要云端同步、多设备同步？
4. 离线时是否允许查看和编辑？编辑后是否需要同步队列？

### 10.4 时间与课表规则

1. 一天的课表节次时间是否固定？每节课的开始结束时间是什么？
2. 是否只支持 1-25 周？
3. 是否需要支持法定节假日、调休、临时停课、补课？
4. 课程颜色是按课程名稳定生成，还是后端返回？

### 10.5 待办规则

1. “有持续时间”的待办是否可以被完成？当前交互说列表不展示完成按钮，但批量完成提示说不会将有持续时间的待办变为已完成，需要确认详情页是否允许完成。
2. 待办重要程度半星如何输入？点击、滑动，还是长按？
3. 重复待办生成规则由前端还是后端负责？
4. tag 是全局用户级，还是每个设备本地？

### 10.6 智能能力

1. 一句话创建待办使用什么 AI 后端？是否已有接口？
2. 截图识别课表使用什么识别服务？是否需要用户确认识别结果后再写入？
3. 下一件事推荐是纯前端规则、后端算法，还是 AI 接口？
4. 大目标拆分是纯手动拆分，还是未来也需要 AI 自动拆分？

### 10.7 验收与发布

1. 每个阶段你希望手动测试到什么程度才进入下一阶段？
2. 是否需要截图对比原型？
3. 是否需要自动化 Widget Test、Golden Test 或端到端测试？
4. Git commit 是否由 AI 每次自动提交，还是先改完等你确认后再提交？

## 11. 当前默认假设

在你回答上面问题前，AI 可以采用以下保守默认值，但必须在实现计划中注明：

- 首发以手机端 Flutter App 为主。
- 先不实现登录，但数据层预留用户维度。
- 先用 mock repository 开发，接口文档同步维护。
- 默认真实应用初始状态为空数据。
- 时间、节次、周次规则先按 `UI/interaction.md` 实现。
- 涉及删除和批量操作必须二次确认。
- 智能能力先做接口边界与状态，不把 AI 结果硬编码进 UI。
- 每个可手测的小功能完成后提交一次 Git commit，但如用户要求先验收再提交，则以用户要求为准。
