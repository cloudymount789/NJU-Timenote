# 当前前后端工作边界梳理

本文档记录截至当前仓库状态的产品技术判断：前端已经完成什么，当前阶段还要补什么，哪些问题接后端前必须确认，哪些能力应推迟到未来。它不替代 `docs/frontend-backend-contract.md`；涉及契约变更的内容只作为待确认项。

## 1. 当前已完成的前端能力

- Flutter Android 工程、路由、主题 token、通用页面基底和通用组件已经建立。
- 首页已接入真实 repository 数据：下一节课、下一件事、DDL 提醒、下拉刷新和 repository 级变更刷新信号。
- 课表已形成本地闭环：按周查询、手动新增、编辑、删除、课程名稳定颜色、周次规则、跨节显示、跨上午/下午切割、冲突排列、截图添加流程壳。
- 待办核心已形成本地闭环：普通/DDL/duration 三类待办、新建、编辑、删除、完成/取消完成、筛选、搜索、tag、批量、拖拽排序、智能排序、重复规则投影、duration 到期自动完成。
- 创建、搜索、推荐和大目标拆分已形成当前阶段替代闭环：一句话创建为本地普通待办，推荐为本地规则，大目标拆分为手动拆分并批量生成 deadline 待办。
- 课程、待办、tag、设置、课程颜色映射、排序状态和重复完成记录已经通过 `shared_preferences` JSON 快照做设备本地持久化；纯内存 source 保留给测试。
- 后端/AI/截图识别边界已有目录与 repository/service 抽象占位，UI 不直接调用 HTTP。

## 2. 当前必须做

当前阶段的主线不是再补大功能，而是把已有本地闭环磨稳定。

1. 完成手动测试清单中未勾选的核心回归，尤其是 Android 竖屏下首页、课表、待办详情、筛选侧栏、底部浮层和键盘场景。
2. 修正肉眼可见的体验问题：阴影被裁剪、首页卡片与底部栏拥挤、课表块留缝或文字过早省略、错误提示排队、空态/错误态不够清楚。
3. 检查数据刷新闭环：创建、编辑、删除、完成、批量、推荐添加、目标拆分后，首页、待办页、搜索页、推荐页是否都能及时看到一致结果。
4. 检查时间逻辑闭环：下一节课计算应使用当前周/当前时间；duration 自动完成触发时机应稳定；DDL 超时应保持未完成但视觉提示明确；重复待办的当前周期投影、完成记录和 7 天清理需继续回归。
5. 检查本地持久化闭环：重启后课程、待办、tag、排序、重复完成记录和设置快照应保留；飞行模式下仍可查看和编辑。
6. 让接后端前的差异清单保持最新，避免契约正文、附录、路线图和代码地图互相打架。

## 3. 逻辑没闭环或需继续验证

- 首页真实数据：已接 repository，但仍要验证返回首页、下拉刷新、创建后自动刷新、当前时间变化后的“下一节课/下一件事/DDL 提醒”是否符合预期。
- 数据刷新一致性：`AppRepositories.changes` 已存在，但搜索结果、推荐结果、详情返回、筛选状态和首页卡片之间仍需手测确认是否都响应写入。
- 时间逻辑：`getNextCourse()` 当前按 `occursInWeek(1)` 计算下一节课，接入真实学期周数前需要确认“当前教学周”来源；duration 自动完成目前在查询/进入列表时触发，是否 App 启动即触发仍待产品确认。
- 本地持久化：已有 `shared_preferences` 快照和测试覆盖，但它是轻量快照，不是可迁移数据库；后续字段变更需要补版本迁移策略。
- 重复待办：当前按规则投影当前周期，不批量预生成未来实例；需持续验证 weekly/biweekly 锚点、超时未完成、删除整组规则、完成记录清理等边界。
- 筛选/排序一致性：筛选后的拖拽排序、智能排序覆盖手动排序、完成后置底、重复投影和已完成置底之间容易互相影响，需要高优先级回归。
- 大目标拆分事务语义：本地实现先校验再逐条创建，通常不会部分成功，但没有真正事务/回滚；接数据库或后端前必须明确如何保证全有或全无。
- 契约差异：`onlyDeadline`、课程更新、取消完成/切换完成、ID UUID、目标拆分默认 tag 等仍是接后端前要处理的差异。

## 4. 体验/视觉待打磨

- 首页：常见 Android 竖屏一屏内容、底部输入栏固定与安全区、卡片阴影不被裁剪、三张卡片宽度和间距仍需按原型细调。
- 课表：周数切换位置、今天高亮只在当前周出现、课程块与表格线间距、跨节块文字换行、冲突块宽度、空课表时仍展示清楚表格结构。
- 待办列表：批量模式、拖拽提示、智能排序入口、完成/取消完成按钮、DDL 超时红色提示和小字符合原型且不挤压。
- 待办详情：重复设置与类型切换的字段显隐、时间选择器默认值、键盘遮挡、半星点击区域和错误提示需要继续体验回归。
- 创建/搜索/推荐/目标拆分：底部浮层、搜索自动聚焦、推荐添加/取消添加、目标拆分步骤返回保留草稿都要保证反馈清楚。
- 全局：错误提示应合并或替换最新提示，避免连续点击时堆叠；所有文案在小屏不能溢出或重叠。

## 5. 当前阶段后端真正需要做什么

当前 App 是本地优先，后端不应承接课程、待办、tag、设置的基础 CRUD。后端当前最有价值的工作是：

- 提供可选服务能力声明，例如 `/health` 和 `/api/v1/capabilities`，让前端知道截图识别、AI 解析、AI 推荐、备份导出是否可用。
- 第二阶段优先做截图识别课程导入服务：接收图片，返回待用户确认的课程草稿列表，不直接写入用户本地数据。
- 后续再做 AI 能力：一句话解析待办、下一件事推荐、自动大目标拆分。后端返回草稿或建议，最终写入仍由前端确认后本地落库。
- 如要做备份/导出，应定位为用户主动触发的文件/快照能力，不默认变成云端同步或后端主数据源。
- 后端可以准备契约测试、错误格式、鉴权预留和部署健康检查，但不要把当前本地 CRUD 改造成必须联网。

## 6. 本地优先边界

应由前端本地完成：

- 课程、待办、tag、设置的新增、编辑、删除、查询、筛选、排序、搜索和本地持久化。
- 首页聚合数据、下一节课/下一件事/DDL 提醒计算。
- 课程颜色稳定映射、周次筛选、课表冲突布局。
- duration 自动完成、重复待办投影、重复完成记录、批量完成跳过 duration。
- 一句话创建当前临时行为、推荐当前本地规则、手动大目标拆分生成待办。

需要后端才合理的能力：

- 截图识别、自然语言解析、AI 推荐、AI 自动拆分等模型或服务端推理能力。
- 用户主动备份、导出、跨设备迁移、未来云同步。
- 服务能力声明、健康检查、后端错误格式和可观测性。

## 7. 接后端前必须确认

- 是否继续坚持“后端不存储用户业务数据”；若改变为云同步，需重新设计登录、冲突解决、同步队列和隐私边界。
- 课程编辑是否补 HTTP `PATCH /courses/{courseId}` 或 `PUT /courses/{courseId}`。
- 普通/DDL 待办取消完成是否补 API；持续时间待办结束后是否允许取消完成。
- `TodoFilter.onlyDeadline` 是否保留独立字段，还是统一用 `kind=deadline`。
- 大目标拆分默认 tag 以契约正文的 `"学习"` 为准，还是以交互和当前实现的“大目标 tag”规则为准。
- 大目标拆分在本地/后端如何提供真正事务语义。
- 客户端 ID 是否必须改成 UUID；如果必须，需安排数据兼容或迁移。
- 当前教学周、学期周数、节次时间是否在设置页进入当前阶段，还是保持固定配置。
