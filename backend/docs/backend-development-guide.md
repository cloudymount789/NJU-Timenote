# NJU Timenote 后端开发指南

本文档整理 NJU Timenote 当前项目结构、前后端边界、核心业务规则，以及后端的推荐实现路线。

项目采用**本地优先（local-first）**原则：课程、待办等用户核心数据默认只保存在用户设备上。远程后端只承担必须联网的可选能力，并尽量采用临时处理、不留存原始数据的方式。

具体 HTTP 请求与响应格式见 [backend-api.md](../../docs/backend-api.md)。

## 1. 项目现状

NJU Timenote 当前是一个使用 Flutter 和 Riverpod 开发的前端原型。应用已经实现主要页面与交互，但所有数据都来自内存中的 Mock Repository，尚未接入设备本地数据库或远程后端。

```text
NJU-Timenote/
├── backend/                  # 后端开发目录
│   ├── app/                  # 远程可选能力
│   ├── docs/
│   │   └── backend-development-guide.md
│   └── tests/
├── docs/
│   └── backend-api.md        # 已有的后端 HTTP API 契约
├── UI/
│   ├── interaction.md        # 产品交互需求
│   └── nju-timenote.pen      # UI 设计稿
└── src/nju_timenote/         # Flutter 应用
    ├── lib/app/              # 路由、Provider 和状态控制器
    ├── lib/features/
    │   ├── home/             # 首页
    │   ├── settings/         # 设置
    │   ├── timetable/        # 课表
    │   └── todos/            # 待办
    └── test/                 # Flutter Widget 测试
```

## 2. 前端数据架构

前端的数据调用链为：

```text
Screen
  -> Riverpod AsyncNotifier
  -> Repository 接口
  -> 当前 Mock Repository
  -> 未来 HTTP Repository
```

Repository 的注入集中在：

- `src/nju_timenote/lib/app/providers.dart`

主要接口与实现位于：

- `features/timetable/repositories/course_repository.dart`
- `features/todos/domain/todo_repository.dart`
- `features/settings/repositories/settings_repository.dart`
- `features/todos/data/mock_todo_repository.dart`

下一步应优先为前端新增设备本地 Repository，并在 Provider 中替换 Mock 实现：

- `LocalCourseRepository`
- `LocalTodoRepository`
- `LocalSettingsRepository`

需要远程能力时，再增加专门的 HTTP 客户端，例如截图识别服务。只要新实现保持现有 Repository 方法契约，页面层通常不需要修改。

## 3. 本地优先的数据边界

### 3.1 默认保存在设备本地

以下数据默认不上传到远程服务器：

- 课程、教师、地点、备注和课表安排；
- 待办标题、内容、地点、时间、优先级和完成状态；
- 标签、搜索历史和筛选状态；
- 学期开学日与节次设置；
- 下一件事推荐所使用的心情、启动意愿和焦虑值；
- 大目标拆分草稿及生成结果；
- 本地备份文件。

Flutter 应使用设备本地数据库持久化这些数据。推荐使用 SQLite，并通过 Drift 等 Flutter 数据库库提供类型安全的数据访问层。

### 3.2 可以在本地完成的能力

以下功能不需要依赖远程后端：

- 课程和待办的增删改查；
- 课程周次筛选；
- 待办筛选、排序与搜索；
- 标签管理；
- 大目标手动拆分；
- 当前规则版本的下一件事推荐；
- 本地备份与恢复。

### 3.3 可选的远程能力

只有无法合理在设备本地完成的能力才调用远程后端：

- 课表截图识别；
- 用户明确选择的 AI 推荐或自然语言解析；
- 用户主动启用的跨设备同步；
- 用户主动创建的分享链接。

远程处理应遵循：

- 默认不持久化请求中的用户内容；
- 不在应用日志中记录原始截图、待办内容或其他敏感数据；
- 临时文件在请求完成或任务过期后删除；
- 上传前明确告知用户将发送哪些数据以及用途；
- 持久化同步和云备份必须由用户主动启用；
- 云备份优先在客户端加密，服务端只保存密文。

### 3.4 后端第一阶段边界

第一阶段后端不接收或保存课程、待办、标签和设置，也不引入用户数据库。

后端第一阶段只提供：

- 健康检查；
- 服务能力与数据处理策略声明；
- 为后续截图识别等临时处理接口预留结构。

## 4. 核心业务模块

### 4.1 课程与课表

课程支持：

- 按教学周查询课程；
- 手动添加课程；
- 永久删除课程；
- 从课表截图识别并导入课程。

关键规则：

- `dayOfWeek` 范围为 1 到 7；
- `startPeriod` 和 `endPeriod` 范围为 1 到 12；
- `startWeek` 和 `endWeek` 范围为 1 到 25；
- `weekRule` 支持 `all`、`odd`、`even`；
- 同一门课程在不同教学周应保持相同颜色；
- 课程时间允许冲突，前端负责并排展示；
- 本地 Repository 查询指定教学周时，只返回该周实际发生的课程。

当前 Mock 根据课程名称稳定计算 `colorKey`。本地 Repository 也应使用稳定算法，或将首次生成的颜色持久化到本地数据库。

### 4.2 待办

待办类型：

- `duration`：有开始和结束时间；
- `deadline`：有截止时间；
- `normal`：无时间要求。

待办支持：

- 创建、查询、修改和删除；
- 标记完成；
- 按日期、类型、状态和标签筛选；
- 搜索标题、内容、地点和标签；
- 批量删除与批量完成；
- 管理标签；
- 推荐下一件事；
- 将大目标拆分为多个待办。

当前 Mock 的默认排序规则为：

1. 未完成待办排在已完成待办之前；
2. 每组内按 `deadlineAt` 或 `startAt` 升序排列；
3. 没有时间的待办排在有时间的待办之后。

批量完成时，`duration` 类型待办会被跳过。本地 Repository 必须保持这一行为。

### 4.3 标签

应用预置以下标签：

- 考试
- 作业
- 讲座
- 会议
- 生活
- 学习

创建待办或更新待办时，如果携带了尚不存在的标签，当前 Mock 会自动将其加入标签库。本地 Repository 应保持该行为。

### 4.4 下一件事推荐

当前推荐功能是规则推荐，并非真正的 AI：

- 优先推荐最近截止的未完成待办；
- 根据心情、启动意愿和焦虑值推荐普通待办；
- 提供一条可添加到待办列表的额外建议。

第一版应在设备本地复刻 Mock 的规则行为。未来可以增加用户主动选择的 AI 推荐，但调用前必须明确提示将发送的数据，并避免服务端留存。

### 4.5 大目标拆分

大目标拆分会把多个子目标批量创建为 `deadline` 类型待办：

- 每个子目标的截止时间为计划日期当天 23:59；
- 默认优先级为 4；
- 当前 Mock 自动添加 `学习` 标签；
- 所有子目标必须在同一个本地数据库事务中创建。

### 4.6 设置、备份与导出

当前前端实际读取：

- 学期开学日期；
- 每节课的开始和结束时间。

备份、导出和节次编辑在前端尚未真正接入。备份应优先导出到用户选择的本地文件；只有用户主动选择分享或云备份时才使用远程服务。

## 5. 推荐后端架构

远程后端是本地优先应用的可选辅助服务。当前业务规模适合使用模块化单体，不需要在第一版拆分微服务。

推荐目录结构：

```text
backend/
├── app/
│   ├── main.py
│   ├── core/                # 配置、隐私策略、错误处理
│   └── api/
│       └── routes/          # 健康检查和可选远程能力
├── docs/
└── tests/
```

推荐技术栈：

- FastAPI：REST API 与 OpenAPI 文档；
- Pydantic：请求、响应和业务字段校验；
- Pytest：单元测试和接口测试。

第一阶段不需要远程数据库。只有在实现用户主动启用的同步、云备份或分享能力时，才引入 SQLAlchemy、Alembic 和 PostgreSQL。

## 6. 数据存储规划

### 6.1 设备本地数据库

| 数据表 | 用途 |
| --- | --- |
| `courses` | 课程及教学周规则 |
| `todos` | 待办主体 |
| `tags` | 本地标签库 |
| `todo_tags` | 待办与标签的多对多关系 |
| `semester_settings` | 学期开学日期 |
| `period_times` | 节次时间 |
| `search_history` | 本地搜索历史 |

### 6.2 远程服务数据

第一阶段远程服务没有业务数据表。

未来若增加同步或云备份，应单独设计远程数据模型，并满足：

- 功能默认关闭；
- 用户可查看、导出和删除远程数据；
- 每条数据具有明确的保留期限；
- 优先保存客户端加密后的密文；
- 不将远程数据库作为 App 正常使用的必要条件。

## 7. 数据校验

本地 Repository 必须执行完整业务校验。任何接收用户输入的远程接口也必须独立执行校验，不能信任客户端。

### 课程校验

- `name` 和 `location` 不能为空；
- `dayOfWeek` 必须在 1 到 7 之间；
- 节次必须在 1 到 12 之间；
- `startPeriod <= endPeriod`；
- 教学周必须在 1 到 25 之间；
- `startWeek <= endWeek`；
- `weekRule` 必须是允许值。

### 待办校验

- `title` 不能为空；
- `priority` 必须在 0 到 5 之间；
- `duration` 必须同时提供 `startAt` 和 `endAt`；
- `duration` 必须满足 `startAt < endAt`；
- `deadline` 必须提供 `deadlineAt`；
- `normal` 不应保留持续时间或截止时间；
- 标签名称去除首尾空白后不能为空；
- 推荐输入的三个数值必须在 1 到 100 之间。

### 大目标拆分校验

- 大目标名称不能为空；
- 至少包含一个子目标；
- 子目标名称不能为空；
- 子目标计划日期不得晚于最终截止日期；
- 整个创建过程必须使用事务，任意一条失败时全部回滚。

## 8. API 契约待明确事项

`docs/backend-api.md` 描述了完整的远程 Repository 契约。采用本地优先架构后，其中课程、待办、标签和设置接口不属于第一阶段远程后端范围，可以作为未来同步服务或兼容接口的参考。

### 8.1 PATCH 清空字段

待办从 `duration` 或 `deadline` 切换到其他类型时，需要清空旧时间字段。

建议约定：

- 字段省略：保持原值不变；
- 字段显式传 `null`：清空该字段。

例如：

```json
{
  "kind": "normal",
  "startAt": null,
  "endAt": null,
  "deadlineAt": null
}
```

### 8.2 截图上传

当前接口示例只包含文件名和 MIME 类型，无法真正识别图片。

第一版建议使用 `multipart/form-data` 上传图片。接口必须限制文件大小和类型，不信任原始文件名，并在处理完成或任务过期后删除原始文件。若识别过程耗时较长，则创建具有短保留期限的导入任务。

### 8.3 筛选与排序

接口文档需要明确：

- 多个标签之间使用任意匹配还是全部匹配；
- 日期筛选优先使用 `deadlineAt` 还是 `startAt`；
- 默认排序规则；
- 搜索结果排序规则；
- 是否需要分页。

为保持当前前端行为，建议标签使用任意匹配，日期使用 `deadlineAt ?? startAt`，并采用第 4.2 节中的默认排序。

### 8.4 重复待办

`repeatRule` 当前只是待办字段，没有定义重复实例如何生成。

第一版建议只保存该字段，不自动创建重复实例。正式支持重复待办前，需要设计实例生成、完成状态和修改范围。

### 8.5 设置编辑

若设置页需要支持编辑，应增加：

- `PUT /settings/semester`
- `PUT /settings/periods`

### 8.6 错误与状态码

建议统一使用以下状态码：

| 状态码 | 场景 |
| --- | --- |
| `200` | 查询或修改成功 |
| `201` | 创建成功 |
| `204` | 删除成功且无响应体 |
| `400` | 请求格式或参数错误 |
| `404` | 资源不存在 |
| `409` | 唯一性冲突或状态冲突 |
| `422` | 业务字段校验失败 |
| `500` | 未处理的服务端错误 |

所有错误应使用 `backend-api.md` 中约定的统一错误结构。

## 9. 推荐实施顺序

### 第一阶段：本地持久化与最小远程服务

1. 初始化无业务数据库的 FastAPI 项目；
2. 提供健康检查和服务数据策略声明；
3. 为 Flutter 选择并接入本地数据库；
4. 实现本地课程、待办、标签和设置 Repository；
5. 将 Mock Repository 替换为本地 Repository；
6. 实现本地备份与恢复。

完成标准：App 离线运行时可以完整使用课程、待办、标签、设置和规则推荐功能，远程服务不可用不会影响核心功能。

### 第二阶段：临时远程处理能力

1. 实现截图上传的大小与类型校验；
2. 实现截图识别；
3. 确保原始文件和识别中间数据按策略删除；
4. 在客户端增加上传前隐私提示；
5. 增加日志脱敏和滥用防护。

### 第三阶段：用户主动启用的云能力

1. 设计客户端加密备份；
2. 实现可选跨设备同步；
3. 实现用户数据导出和彻底删除；
4. 实现临时分享链接；
5. 根据需求增加可选 AI 服务。

## 10. 测试重点

后端测试至少应覆盖：

- 单双周课程筛选；
- 课程周次和节次边界；
- 三种待办类型的字段约束；
- PATCH 保留字段与清空字段；
- 多条件待办筛选；
- 搜索大小写不敏感；
- 未完成与已完成待办排序；
- 批量完成跳过 `duration` 待办；
- 大目标拆分的事务回滚；
- 删除不存在资源时返回 `404`；
- 核心功能在远程服务离线时仍可使用；
- 远程接口不会意外持久化或记录用户内容；
- 临时上传内容会按保留策略删除；
- 用户主动启用的云数据可导出和删除。

## 11. 开发原则

- 核心用户数据默认只保存在设备本地；
- 核心功能不依赖远程服务可用性；
- 数据上传必须由用户操作触发并提前告知；
- 远程服务默认不持久化用户内容；
- 本地 Repository 和远程接口都必须执行数据校验；
- 保持现有 Repository 方法语义，降低前端接入成本；
- 对本地批量写入和多资源创建使用数据库事务；
- 云端持久化功能必须可选、透明、可导出、可删除；
- 所有时间戳使用带时区的 ISO 8601 格式。
